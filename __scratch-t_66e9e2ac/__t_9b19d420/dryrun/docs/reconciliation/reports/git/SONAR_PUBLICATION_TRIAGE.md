## Finalidade real e ações proporcionais

### Execução de fontes locais nos probes

Há dez avisos de execução dinâmica e um aviso adicional de code injection no mesmo `vm.runInNewContext` de Skins. Os probes executam hooks, worker, helpers, bootstrap e SDK reais para reproduzir os defeitos observados, usando dados sintéticos e dependências simuladas. Alguns apontamentos são chamadas posteriores da função já compilada, não novas origens independentes. O README orienta usar uma cópia temporária do pacote com o checkout preservado no baseline. [Instruções publicadas](https://github.com/adm01-debug/Zapp_Web_V2/blob/9a1c370c1979b5e3f1c59291a2bfac331f689e3d/docs/reconciliation/reproduce/README.md).

Essa finalidade não transforma os scripts em endpoints de produção, mas a confiança no código carregado deve ser explícita. Cross-module confirma HEAD, porém lê arquivos do worktree sem comparar os hashes esperados antes de executá-los; um HEAD correto sozinho não detecta arquivos alterados. Multiplix e Skins registram o baseline no relatório, mas não o impõem antes de carregar todas as fontes. Mocks de fetch/DB/provedor comprovam o isolamento das dependências previstas, não autorizam executar um checkout arbitrário como se fosse seguro. A ação adequada é fixar/validar conteúdo e fronteira de execução, mantendo a reprodução do código real; não declarar todos os sinks falsos positivos nem mudar exclusões para obter verde.

### Argumentos e caminhos do validator

O `subprocess.run` da linha 60 usa uma lista e não usa shell, portanto o alerta não demonstra injeção de Bash. Há, porém, uma lacuna real: `definition_ref` e `path` vêm do registry sem validação sintática antes de formar um argumento de `git show`. A validação de refs fixadas/caminhos, do executável Git e da política de saída é proporcional. Os dois alertas da linha 86 tratam do mesmo `--output`, escolhido explicitamente pelo operador de uma CLI local; não são duas vulnerabilidades remotas. O hardening foi tratado separadamente deste diagnóstico congelado. [Validator congelado](https://github.com/adm01-debug/Zapp_Web_V2/blob/9a1c370c1979b5e3f1c59291a2bfac331f689e3d/docs/reconciliation/reproduce/validate_package.py#L54-L86).

O SHA-1 da linha 63 é **identidade Git blob**, calculada com cabeçalho/tamanho/NUL/conteúdo. Não protege senhas. Substituí-lo por SHA-256 quebraria a comparação com os IDs Git. Explicitar a finalidade não criptográfica é apropriado; o manifesto do pacote já usa SHA-256.

### Falso positivo de segredo comprovado

`skins-probe-results.json:9` contém o fingerprint SHA-256 de `src/styles/tokens.css`, dentro de `source_hashes`. Recalculei esse hash do baseline e ele coincide com o publicado: `ca19bfc1a5fd31d443e2763da0304e73bc25027cd894add5d0a32d015f805a28`. **Não é credencial ou token de autenticação.** A evidência não deve ser apagada ou modificada para esconder a palavra `tokens`. Prova no JSON de hardening; [linha publicada](https://github.com/adm01-debug/Zapp_Web_V2/blob/9a1c370c1979b5e3f1c59291a2bfac331f689e3d/docs/reconciliation/evidence/skins-probe-results.json#L6-L10).

### Regex, ordenação e fixture

Os cinco avisos de regex recaem em parsing de imports, CSS ou bootstrap de arquivos locais. O custo em uma fonte malformada merece transformação mais previsível/limites de tamanho, mas os apontamentos não demonstram DoS remoto no produto. Os dois avisos de ordenação recaem na mesma linha 41 de Skins: as listas são usadas somente em operações de pertencimento/contagem, então `sort()` é redundante e pode ser removido, sem comparator artificial.

A expressão `!== null` em Cross-module:150 é verdadeira por construção porque as duas linhas sintéticas têm `first_response_at` preenchido. Isso documenta que o contraexemplo é permitido pelo índice parcial de SLA; não é uma condição morta de negócio. Pode ser exposta como uma pré-condição explícita do modelo, preservando sua finalidade. Não há justificativa para mudar o SQL ou o código do produto com base nesse aviso do probe.
